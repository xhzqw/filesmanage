# CDW G12：DHF/DMR 专用签批权限与逐次全新 PostgreSQL 验收库

本技术记录不等于已发布的公司正式签批授权或合规制度。

## 目的

1. 废止历史复用的固定 `cdw_g2_tasks_iso_20261015` 测试库作为 G2–G11 的可写集成测试目标。运行器 `scripts/cdw_fresh_pg_lab.sh` 每次创建带不可预测 16 位十六进制后缀的独立 PostgreSQL 空库，用正式迁移器从 `0001` 开始应用所有迁移并运行真实事务测试，退出时仅销毁本次创建的库。测试必须同时校验数据库名和进程内部的本次测试环境凭据，否则拒绝插入测试数据。
2. `ZS-QP-09` 委托的 DHF/DMR 专用签批权限不得由普通 QMS 受控程序、管理员设置模板或文档名切换直接推定。新增受控文件 ID、专用工作流模板 ID 和相应专用制度受控发行 ID 三者的**绑定证据**。
3. 登记由管理员显式提报。源政策必须为生效中的 QMS 类受控发行，且专属源文件应可核对为《产品设计历史文档管理规定》或《产品器械主文档管理规定》（支持文档标题写法变体）；源文件不能就是被审批的对象文件。另一名具备被审批文件实时文控角色、可以访问源文件的人员对原始条款和节点进行独立核验。提报人不能自审。
4. 只有当前有效、匹配文件/文件种类/模板/政策版本并已独立核验的证据才能打开正式提交、签署及候选文件后续发行的门禁。源制度退役、变更有效版本、专项核验被撤销后立即拒绝未来签署/发行。历史签署与审批实例保留，不自动撤销已完成的合法流程。
5. 数据库直接插入审批实例或决定的请求，同样调用 `cdw_qms_special_authority_current`，不允许绕过 API。文档一旦拥有专项审批登记，改名不能抹除原先文件 ID 的 DHF/DMR 标记。专用制度本身与需要按该制度批准的产品文档分开识别，防止循环审批。
6. 后台管理登记与核验共用 `CDWQMSSpecialAuthorityPanel`，嵌入既有「正式审批」和「任命核验」的 RareUI 工作区，不建立第二套功能。

## 不代替的业务事实

- 系统只能证明源文件是**经过受控发行且有双人复核记录**的版本；并不能凭文件标题自动鉴别法律效力、审批人真实任命、签字真实性或符合 ISO 13485 / 注册法规的全部细节。原文档缺失时保持阻断。
- 如真实公司规定将 DHF/DMR 专门审批文件另有名称，不能单凭管理员改名称绕过检查，应经文控核实原件并通过后续受控配置变更调整目录规则。
- 源制度、岗位任命、培训资质、电子签名法律等效性以及制造生效条件是相互独立的义务，当前专项登记不会替代任一项。
- 开发环境仅使用隔离测试生成的模拟文件/审批数据验证技术门禁。不改原始 `docs/流程参考文档/`、8091 入口，也不在业务库虚构企业质量事实。

## 尚未授权宣称完成的部分

本阶段交付的是**可运行的受控资格核验底座**，而不是企业已正式批准的 DHF/DMR 审批矩阵。实际执行必须先完成原件上传、文件类别确认、受控发行、真实有效的签批岗位任命，以及适用法规和电子签署效力的人工核定。暂未提供专项依据“待审核提报退回/驳回”的完整状态机、跨部门专项资格撤销通知与实体政策条款逐项机器校验；这些不能因 G12 自动视为已经交付。
