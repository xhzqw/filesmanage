# 搜索“秒搜”专项：冷热查询分流、输入即搜与真实 Chrome 验收（2026-10-11）

## 目标与范围

将文件名、正文关键词和目录名的通常搜索体验缩短到用户输入后的 1 秒以内。这里不假定缓存命中，也不把 API-only 耗时冒充最终可见耗时。保留用户/目录 ACL、全文查询语义、分类/标签/日期/上传人筛选、排序、游标分页、无权限数据隔离。

## 实施内容

1. **`0025_search_name_trigram.sql`**：新增 PostgreSQL `pg_trgm` 及有效文件名、有效目录名的 GIN trigram 索引；重命名与删除事务同步维护索引。与已有 `file_text.tsv` GIN 全文索引互补，原有 `ILIKE` 通配语义保留。
2. **按候选数量分流**：以每路最多 257 条的有上限、非权限裁决候选探测选择 SQL 执行路径。候选较少时用分别走文件名 trigram GIN/正文 tsvector GIN 的 ID UNION，随后在外层统一应用原有授权范围、筛选、排序和游标；候选较多时保留旧版可提前达到 LIMIT 的顺序扫描，避免把 100k 广泛匹配结果全部 UNION 排序。短词回退原策略，避免 trigram 对单字符低效。候选探测不决定可见结果与总数，全部真实业务结果仍严格执行服务端权限过滤。
3. **输入即搜**：`SearchPanel` 的文件名/正文输入框在输入停顿 180ms 后自动检索，不再要求按搜索按钮；保留按钮与高级筛选。输入变化即使正在等待防抖，也会使旧结果失效，新的首屏永远替换而非叠加；提交新查询会 Abort 前一请求，`loadMore` 游标/去重、失败重试仍独立。中文 IME 拼音组成过程中不发请求，待 compositionEnd 后搜索。
4. **可复验工具**：`scripts/perf_search_probe.py` 对独立 100k 文件数据执行冷/热 API 搜索（每个关键词首次与重复），`scripts/perf_large_tree_browser_check.mjs` 扩展真实 Chrome 输入到可见结果的测量。隔离浏览器与压测服务固定 `filesmanage_perf` + 本机 `127.0.0.1:18094`。

## SQL 执行计划（100,466 文件）

对于 `pf_bulk_9627` 这类只有 8 个匹配的文件名，索引创建后旧版 `OR EXISTS` 计划依然扫描 100,466 行，`EXPLAIN ANALYZE` 计数约 168ms；索引候选 UNION 计划使用 `ix_files_active_name_trgm`，相同计数约 2.3ms。对“文件”这类宽词，强行 UNION 曾测出约 2.5s，故本次专门保留宽词旧路径。

## 真实 API 基准（隔离库，单位 ms）

| 关键词 | 旧 SQL 未增加新索引之前的首次 HTTP | 新索引+分流后的首次 HTTP |
|---|---:|---:|
| `pf_bulk_9627` | 1083.0 | 24.0 |
| `pf_bulk_9626` | 354.4 | 16.9 |
| `pf_bulk_9625` | 325.6 | 21.7 |
| “文件” | 330.9 | 306.5 |
| `pf_ord` | 67.6 | 25.6 |
| “导出” | 350.9 | 401.5 |
| 不存在词 `qq___nonexistent_9876` | 438.5 | 11.5 |

两次为独立重启后的每关键词首次响应，每个关键词重复请求的暖缓存通常为 1–6ms；不是同一冷热状态的严格 A/B，也不是 p95。无跨机器容量与硬件比较。**“导出”本次没有改善**，不得宣称所有全文匹配都加速。

| 场景 | 单次浏览器墙钟耗时 |
|---|---:|
| `pf_bulk_9627`，8 条 | 304ms |

## 仍需持续改进

1. 正文大词/中文短词的全文查询通常仍达 300–400ms API，可进一步研究语言分词策略以及权限 CTE 的代价；
2. 暂无严格的高并发 p95 与公网环境下 1 秒搜索 SLO；本轮只证明上列真实单次样本；
3. 高级筛选仍在“应用筛选”按钮后执行，以免日期、范围、上传人多字段输入时发送大量不完整查询。
