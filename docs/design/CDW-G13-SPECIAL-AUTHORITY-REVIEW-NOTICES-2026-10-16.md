# CDW G13：专项签批依据逐节点条款核验、退回/驳回及收件通知

本技术记录不构成企业已经批准的质量程序或法定签批资格。

## 工作流

- 管理员在既有正式审批工作台针对 DHF / DMR 文件、审批模板版本和已受控生效的专属制度发行版本提报资格。每个正式审批节点必须独立登记 `nodeKey`、`clauseRef`（原制度条款编号）及 `basisSummary`（该条款对应岗位的适用性说明）；节点必须完整、一一对应于已发布模板的真实节点，无缺项和重复。记录随提报锁定，不容许后改。
- 独立文控核验时可选择“通过”（`pending → verified`）、“退回补证”（`pending → returned`）或“驳回依据”（`pending → rejected`）。已通过授权可以撤销（`verified → revoked`）。退回与驳回也是原记录不可逆的终态；要补材料或重新申请，必须生成新申请并履行独立核验。
- 每次退回/驳回与撤销在**同一事务内**产生针对收件人的持久通知。退回和驳回通知提报人；撤销通知提报人、原独立核验人和模板批准人。通知只允许本人独立“已知悉”并记录时间；业务消息不声称短信或邮件已送达。
- 专用制度及文件 ACL、文控角色、提报人不得自审、完整的条款节点对应、源政策当前有效指针，以及正式签署岗位资格是互不替代的安全条件。原先已提交但没有逐节点证据的记录历史保留，不能自动获得新的有效授权。
- 原 0062 只处理通过/撤销且没有专用通知；新增 `0063_cdw_qms_special_review_actions.sql`，不改写已应用迁移。应用/端口/前端使用相同真实状态机，审计事件和 outbox 同事务生成。

## 本阶段验收原则

使用 `scripts/cdw_fresh_pg_lab.sh` 每次新建隔离 PostgreSQL 库，应用全部迁移、完成 G2–G13 回归、自动销毁测试库；同时执行 Go 编译与静态检查、TS/Vite、OpenAPI 与架构检查、18091 开发部署和 Chrome 1440/1024/780 浏览器实测。**8091 未授权，不得使用演示数据在业务库生成公司任命、制度或真实审批。**
