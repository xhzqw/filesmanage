# CDW G17：正式审批血缘与双轨责任闭环

本阶段复用现有正式审批和任命核验工作台。中断审批只能作为只读历史，新审批必须有独立冻结稿、现行审批模板、原流程规定的岗位任命和全新签署决定。

## 技术边界

1. 相同**文件 ID**产生了尚未关联后继的隔离审批时，不能通过更换交付稿 ID 绕过重新审批的血缘关联。正式审批发起事务先对已经加锁的实际文件 ID 运行待继承检查（而非交付稿 ID），再调用既有有效模板/任命/冻结稿核验；没有 `replacesApprovalId` 则失败关闭。同文件已有后继的旧中断审批不再阻止其他合法的新版本审批。
2. 一笔中断审批最多一个**直接后继**。数据库新的唯一索引保护链路不分叉；再次中断后，应把下一个新流程链接到最近的中断后继，不得向前随意跳接到已经有后继的旧实例。该迁移不会自动修正已存在的重复记录；若检测出重复则拒绝迁移，必须人工依法核对。
3. 新增只读血缘端点 `GET /api/workbench/qms-formal-lineage/{id}`。从任意审批实例沿不可变前驱回溯根节点，再向后顺序检索全部后继（请求上限 31 个节点，另标识截断）；逐个返回真实 SHA-256、模板版本、制度发行 ID、当前状态、实际签署批准/拒绝/待处理计数、已批准候选记录，以及真实通知收件及阅读数。查询首先验证原申请人/原节点参与人或当前文控的**历史读取资格**及源文件的实时 ACL，再在整条链逐一核验文件预览权限；历史读取资格不等于当前签署资格，不将读接口作为历史审批恢复或法规有效性的证明。
4. UI 复用一个 `CDWFormalLineagePanel` 用于现有正式审批详情以及文控中断历史。无需独立导航或新的 UI 库。**受控批准**与**通知确认**严格独立：待确认收件人不会被显示成批准者；新批准候选文件也不会冒充已经生效的受控发行。
5. 隔离 PostgreSQL 验证跨实例祖先/后继一致、已完成签字数及通知计数、直接后继唯一、非法分叉事务回滚、既有 G2–G16 门禁。开发构建和 Chrome 三宽验收通过后才对 18091 应用新迁移。8091、原始程序和已有未提交改动不得触碰。
