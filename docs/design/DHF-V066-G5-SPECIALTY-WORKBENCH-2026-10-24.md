## 1. 与现有审批工作台的真实兼容性

审查已有 `internal/domain/workflow.go`、`ports/workflow.go`、`postgres/workflow.go`、`web/src/pages/Approvals.tsx` 后确认：现有 `approvals` 包含文件修改/回滚审批及已存在的逐级审批链，承担 CDW 文件版本、ONLYOFFICE 保存和历史责任记录，**不得误认为弃用代码而整表删除**。因此 V0.6.6 **删除旧误导性的 /workspace→收藏 跳转**，把该入口指回实际工作台，保留老文件审批的交易边界和原始历史数据。

同一个 `/approvals` 工作台新增“研发阶段审核”侧栏入口。文件修改审批与 DHF 阶段审核可以并列显示，但拥有不同领域身份、记录和业务决策，不共用一个批准状态。

## 2. 新增数据库与责任模型

`migrations/0047_dhf_pilot_workbench_review_tasks.sql`：
- `dhf_pilot_review_assignments`：项目＋阶段＋专业审核键 → 指定审核人；必须已经是项目成员且账号有效。
- `dhf_pilot_workbench_tasks`：每个提交 × 审核键恰好一项任务，任务不可改派、不可覆盖或删除。
- G5 任务键：模板列出的每个专业（例如 `G5-SW`、`G5-MF`）+ `__gate__` 总阶段审核。
- G6（首次转移）仅独立 `__gate__` 阶段任务；与 G8 身份分离，绝不因名字相似自动复用。
- 禁止提交人审批自身提交，禁用用户不可指派。缺失责任配置、配置多余、冻结后试图删除已用分配均阻断。
- 尚无电子签名和正式审核决定状态机：任务 `pending` 在本版仅供**只读查看**，触发器禁止未经签审的状态变更。

`DHFPilotPersistSubmission` 在原有 SERIALIZABLE 提交事务内派发全部审查任务。任务写入失败则阶段 `submitted` 状态、证据包、audit 和所有已创建任务一起回滚；不允许“先成功提交，稍后尽力派发”产生无人负责的悬空包。

补充：`migrations/0048_dhf_pilot_review_assignment_history.sql` 禁止已经派发过的审核配置被改写；同阶段审核人默认必须相互独立，不能将一个人同时配置为专业审核和总 Gate；插入任务时再核对已发布模板确实包含该审核键、派发人确实是提交人。历史配置需要变更时，应通过后续受控版本或授权改派事件实现，而非更新旧审核记录。

## 3. 工作台 API 与 UI

- `GET /api/workbench/dhf/tasks`：仅认证后执行；同一个只读 Repeatable Read 事务，重新读取数据库用户有效性。
- PostgreSQL 按**实际被指派人**过滤 `reviewer_id`、项目 active、有效账号、模板 published、待审状态，限制最多 100 项，不允许管理员查看所有任务的隐式越权。
- 返回对象仅包含任务、项目/阶段/提交身份、审核键、分配时间；不包含文件字节、文件 SHA、其他人的数据或审批权限。
- `web/src/pages/Approvals.tsx` 复用现有双栏工作台，新增“研发阶段审核”入口，按用户任务显示列表+详情。
- 原 `/workspace` → `/doc?view=favorites` 误路由被替换为 `/approvals`，导航统一标为“工作台”。
- 不创建第二套独立“任务”应用，不删除现有 CDW 文件审批数据结构。
- 本阶段未提供签名/退回动作按钮；这些动作必须等不可变审核决定、真实授权链、责任跳级策略完成后才能安全开放。

## 5. 尚未执行的正式审批

**P0：** G5 专业审核意见必须与同一冻结 `submission_id/manifest_sha/policy_sha`、审核签署人、角色与步骤版本绑定；总 Gate 必须等待适用专业全部完成。流程模板默认逐级回签，可授权跳级，但原中间责任不能自动消失。审核决定、退回和条件放行必须分别有不可变事件及整改关联。实现前，新任务只能展示“待审核”，不能通过技术按钮将项目或文件标为“已通过”。

DHF 原始大纲来源节点是候选集合，仍不能自动转为全部必交文件或正式责任人。真实业务模板发布需授权核准。
