# CDW G20：制度授权的站内升级与独立处置闭环

G20 延续 G19 跨文件统计与审计，不创建默认企业规定，不直接修改 ERP、OA、质量法规批准数据，不发送外部邮箱、短信或消息。正式审批、受控发行、个人通知已读和异常升级是四套不同事实，不能互相代替。

## 状态和权限

- 新增 `0069_cdw_qms_authorized_escalation.sql`，建立有效制度**待核验规则**、独立文控核验（`pending → verified`）与独立撤销（`verified → revoked`）。提报必须提供目标文件、精确的已经生效并处于有效指针上的受控发行 ID、原制度条款、**明确分钟数**、有当前 `document_control` 任命的接手人员和不少于16字的来源核验说明。原提报人不得自核验；原提报人与首次核验人亦不能擅自撤销已核验规则。参数不可修订；需更换应由授权文控撤销后重新提报。失效制度不再允许新升级。
- **升级事件不是定时任务**。只有已经由 G18 独立人工督办且截至申请时仍未确认、真正超过被独立核验的显式时限、制度当前有效、负责人与发起文控仍有任命的单条通知，才允许人工建立一条站内升级事项；每通知 UNIQUE 一案。不会自动声称“违法逾期”，不会发出企业外部消息。
- 新升级事项可由受任人员查看，**独立文控**记录处理结论（不少于16字）。发起人不可自结案、原事项及结案记录不能修改或删除，二次结案被阻断。通知个人已读不能自动关闭异常，站内升级也不能替代原正式审批。
- G18/G19 的文控审计包继续包含所有原签署节点及个人通知，并新增 G20 逐人升级事实（制度发行 ID、条款、明确时限、升级发起人及接手人、处理说明和独立结案时间）。G19 离线校验兼容旧版本审计包，并在新导出内容包含 `escalations` 时逐条验证其审批节点属于该分段，避免跨文件混入其他案例。
- 提报、核验、撤销、升级和结案均复用 G7 事务幂等/文件 ACL/强制审计设施。查询前运行当前角色范围过滤，应用层再次核验实时文件 ACL。审核者核验原制度文件访问权限。

## 工作台与测试

- 原 QMS 专项文控工作台复用 RareUI 增加一个简洁的可折叠“受控通知升级”模块：按真实文件列表登记依据、独立核验/撤销、针对已人工督办且未读的通知申请人工升级、独立记录关闭。无新顶栏 Tab、无重复流程引擎。
- G20 隔离测试使用专用保存点创建虚构但内部一致的有效受控程序与岗位授权，核对未督办不能升级、错误时限阻断、相同通知去重、发起者自核验/自结案拒绝、真正独立关闭及规则独立撤销，然后完全回滚，**不会向开发业务库写入任何公司升级时限**。
- 生产级验收要求：全新 PostgreSQL 完整迁移及 G2–G20 回归、TypeScript/Vite、Go build/vet、OpenAPI 合同、架构检查、真实 Chrome 1440/1024/780，最后仅部署 18091；8091、原始制度和已有用户工作树修改保留。
