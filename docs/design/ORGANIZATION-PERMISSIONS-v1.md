# filesmanage v2.1 — 组织与权限管理一体化设计规格

> 状态：设计评审通过；P0 实施中（未完成远端门禁前不视为已验收）  
> 版本：v1.0-draft · 2026-10-09  
> 源码核对：`10.144.144.1` / `openclaw77`，`/root/repository77/filesmanage-v21`，Git `7988fc6`（与本地副本同一提交）。  
> 适用：Go/Gin + PostgreSQL + React/TypeScript 现有项目。不得以旧 Node demo 作为事实来源。

## 0. 决策摘要

将顶级导航“组织管理”命名为 **组织与权限**（若导航空间不足，顶栏仍可写“组织”，页面标题为“组织与权限”）；**权限管理内置于该页面，不新增顶级导航入口**。在当前“部门成员 / 工作组管理”右侧主工作区加入第三个 Tab“权限管理”。

业务边界：

- **部门**：人员组织关系、筛选范围；不是自动获得文件权限的 ACL 主体。
- **工作组**：现有可授予 ACL 的主体，跨部门组织协作；成员变化影响有效权限。
- **管理角色**：对组织、组、ACL、审计和策略的操作职责（RBAC）。目前代码以 `is_admin` 为主，细粒度角色属于后续演进，不能先做一个虚假的“角色管理”按钮。
- **资源 ACL**：决定用户/工作组对特定目录的九种文件动作，保留当前继承、`scope_only`、有效期、正向并集语义。管理能力（如 `manage_acl`）不混入九种文件动作。
- **共享授权**：文件或目录对具体用户/组的受限正向授权，必须跟目录 ACL 在同一授权决策路径下判断。不得把内部分享反向解释成 ACL 管理权。

此次 P0：统一入口、管理交互、复用既有 ACL；P1：服务端有效权限解释；P2：细粒度管理角色与安全策略。任何阶段不得因页面改造扩大授权能力。

## 1. 现状事实与待解决项

当前主导航在 `web/src/shared/ui/AppShell.tsx` 将 `/org` 显示为“组织管理”；`web/src/features/organization/OrganizationPanel.tsx` 仅提供 `members`/`groups` 两个 Tab。文档页 `web/src/pages/Documents.tsx` 使用 `features/folders/GrantDialog.tsx` 直接编辑目录授权，调用已存在的：

- `GET /api/folders/:id/acls`（列出直接授权）
- `POST /api/folders/:id/acls`（新增授权）
- `DELETE /api/acls/:id`（撤销授权）

数据库 `migrations/0001_core.sql` 已含 `users`、`departments`、`workgroups`、`workgroup_members`、`acls`。`acls` 含 `folder_id, subject_kind, subject_id, actions, scope_only, expires_at, granted_by`，动作限定为九种文件操作。P0 不重建表或批量迁移 ACL。

需要纳入安全整改：

1. `application.ListGrants` 当前对非管理员仅要求该目录的 `list`，可返回授权明细；这与 `docs/SPEC-v2.1.md` §2.5 要求“ACL 明细必须有管理能力”不一致。P0 应将读取他人 ACL 明细限定给管理员（或真正服务端验证的后续被委托角色）。普通用户只能读取**自己的有效动作**，且不能泄漏别人的授权记录。
2. `application.AddWorkgroupMember/RemoveWorkgroupMember` 当前没有显式 `bumpACLEpoch`。需要结合读缓存/授权查询做并发回归，确保成员变更提交后新的资源请求立即观察到更新后的权限。
3. `application.RevokeGrant` 在事务提交前调用缓存失效；应核查并规范为“成功提交后失效”，避免提交前发生读写交错和旧缓存残留。其他写入权限相关流程一并核查。

上述为静态源码审计问题，未经远端测试复现；不能宣称已经修复。

## 2. 页面信息架构

### 2.1 顶部导航

保留一个 `/org` 路由，导航名称“组织与权限”（缩屏时可简写“组织”）。不要在顶部新增“权限”“角色”“审计”的并列顶级入口。

### 2.2 页面一级分区

| 分区 | 状态 | 功能 | 权限 |
|---|---|---|---|
| 部门成员 | P0 已有、优化 | 组织树、用户增删/冻结/重置密码、部门筛选 | 现阶段仅系统管理员 |
| 工作组管理 | P0 已有、优化 | 工作组、成员变更、组权限入口 | 现阶段仅系统管理员 |
| 权限管理 | P0 新增 | 按目录授权、按用户/组查询、授权撤销 | 现阶段仅系统管理员 |
| 角色管理 | P2 实现后启用 | 管理角色定义、授予范围、职责能力 | 系统管理员 / 受限角色管理员 |
| 权限审计 | P1/P2 实现后启用 | ACL 与角色授权变更记录、操作者、影响范围 | 具有 `view_audit` 管理能力的人 |
| 安全策略 | P2 实现后启用 | 默认授权、安全委派和高危操作规则 | 系统管理员 |

**未实施的分区不得呈现为可用的假按钮。** P0 实际可交互 Tab 保持三个（部门成员 / 工作组 / 权限管理）；其余放入路线图，不占用生产界面空间。

### 2.3 URL 和状态

- 统一：`/org?tab=members|groups|permissions`
- 权限管理内部模式：`/org?tab=permissions&view=folder|subject`
- 目录定位：`&folder=<opaque-id>`；从文档页快捷入口使用该 URL。
- 页面刷新/浏览器前进后退恢复 Tab、选择的资源；搜索字词可仅存在页面状态。
- 非管理员直接输入 URL 不会获得权限；所有管理端点独立做服务端校验，不依赖前端路由隐藏。

## 3. 权限管理交互合同

### 3.1 “按目录”视图（主路径）

```text
┌────────────────────────── 组织与权限 ──────────────────────────────────────────┐
│ 部门成员 │ 工作组管理 │ [权限管理]                                          │
├────────────────────┬─────────────────────────────────────────────────────────┤
│ 资源目录树          │ 目录：研发 / 机械设计 / 组件                            │
│ 搜索目录            │ [按目录] [按成员/工作组]           [新增授权] [刷新]     │
│ ▾ 所有目录          ├─────────────────────────────────────────────────────────┤
│   ▾ 研发部          │ 授权主体    来源       操作权限          生效范围  到期   │
│     ▸ 机械设计      │ 机械设计组  直接       预览/下载/上传     当前及子树  —  │
│   ▸ 制造部          │ 张三        直接       列表/预览          仅当前    ...  │
│                    ├─────────────────────────────────────────────────────────┤
│                    │ 有效权限说明：直接 + 祖先继承 + 有效内部分享，以服务端    │
│                    │ 判定为准。点击主体查看每个动作的来源与到期时间。          │
└────────────────────┴─────────────────────────────────────────────────────────┘
```

资源树不等于部门树。权限 Tab 的左栏必须切换为**目录资源树**，显式使用“资源目录”标题；不能用部门层级伪装成目录权限继承关系。选中资源后右侧显示目录路径、直接授权列表、过期/范围、操作人；P1 上线后补充有效权限解释。

空状态：未选择资源展示“选择目录以查看授权”；无直接授权展示“本目录没有直接授权，可能仍存在继承或共享权限”；403 展示无管理权（不显示授权明细），404 不泄漏额外路径。

### 3.2 “按成员/工作组”视图（排障主路径）

左侧提供真实用户/工作组的分页搜索，不预加载全部用户。右侧按可访问目录分页展示已授动作；筛选“有下载权 / 可修改 / 含过期授权 / 仅直接授权”等。全局可见性范围必须由服务端返回，前端不能遍历所有资源并自行计算他人的权限。P0 如没有支撑接口，只可展示“该主体的直接 ACL 记录”，并醒目标注“非最终有效权限”；P1 服务端支持后方可命名“最终权限”。

### 3.3 新增授权

选择目录 → 选择主体类型（用户/工作组）→ 搜索并选中有效主体 → 勾选动作 → 选择作用范围（**默认仅当前目录**，修改为“包括子目录”需显式选择）→ 设置可选到期时间 → 预览摘要 → 确认写入。

九种文件动作：`list`、`preview`、`upload`、`download`、`modify`、`delete`、`rename`、`move`、`print`。允许的动作集合必须由服务端校验；`manage_acl/manage_users/view_audit` 不进入此表单。`print` 的实际操作仍须 `preview`；移动需按现有源/目标权限规则执行，勾选一个动作不自动开启其他动作。

表单风险提示：

- “包括子目录”标示继承范围及影响估计（没有安全估计接口则不报数字）。
- `delete`、`modify`、`move` 和 `download` 等高影响操作应突出结果摘要，但不能只靠颜色传达。
- 过期检查以服务器时间为准；无效主体、禁用主体、无授权资格、目录已删除均由服务端拒绝。
- 提交失败原表单保持；网络状态未知不要声称成功，重新读取服务端再判断。

### 3.4 撤销及重复授权

撤销前显示“撤销的是哪条**直接授权**，该主体仍可能通过工作组、祖先或共享取得同样能力”。撤销成功后从服务端重取，不用前端模拟有效权限。重复授权合并、冲突和并发写入策略遵从后端既有规则；如需更改必须先立单独 ADR，禁止暗中改变正向并集语义。

### 3.5 文档页快捷入口

保留目录右键/工具栏的“管理权限”操作，仅管理者可见。点击后进入 `/org?tab=permissions&view=folder&folder=<id>`，保持原目录 ID 并返回时恢复文档定位。不再维护一个与中心授权列表、校验流程不同的独立 UI；过渡期 `GrantDialog` 可以短期复用同一底层组件，但必须最终只有一套数据操作/校验逻辑。

## 4. 有效权限解释的设计（P1）

后台成为**唯一可信判定与解释来源**；不得使用前端 `ACL.actions`、`isAdmin`、组成员和祖先目录在浏览器中拼凑“最终可执行权限”。现有 `resolveActions` 决定授权结果，应抽取稳定的领域/应用层解释模型，返回实际允许的动作及可披露的来源。

候选管理员只读端点：`POST /api/permissions/explain`（防止主体 ID 大量落入代理 URL 日志），请求：

```json
{"subjectKind":"user","subjectId":"u_...","folderId":"f_..."}
```

响应草案（精确字段以 OpenAPI ADR 定稿为准）：

```json
{
  "subjectKind":"user",
  "subjectId":"u_...",
  "folderId":"f_...",
  "effectiveActions":["list","preview"],
  "sources":[
    {"kind":"direct_acl","resourceId":"f_...","actions":["list"]},
    {"kind":"inherited_acl","resourceId":"f_ancestor","actions":["preview"],"expiresAt":null}
  ],
  "evaluatedAt":"2026-10-09T14:00:00Z"
}
```

注意：示例只展示来源形状，并不表示已有此接口。还要支持 `workgroup_acl`、`folder_share`、`file_share`（文件粒度另行设计）及 `admin_override`。共享的主体可能来自用户或工作组。过期、撤销或无效主体的授权不得进入生效动作；需要时以单独 `ignoredSources` 向管理员解释失效原因，谨防暴露敏感路径。必须能指明 `scope_only` 为何没有传播到子目录。

普通用户若需要“我的可操作动作”，设计独立 self-scoped 只读接口，绝不允许任意传 `subjectId` 读取他人的 ACL。大型矩阵使用严格上限的批量查询/服务端分页，不在前端发 N×M 次请求。

**说明：** 这是候选 API；上线前要与现有 `docs/design/COMPLEX-WORKFLOWS-v1.md` 的 ADR-UX-04 合并评审，避免两种权威接口并存。

## 5. 管理角色模型（P2，不能冒充 P0）

当前 `domain.User.IsAdmin` 表示系统管理员；建议后续引入独立的 `ManagementCapability`（如 `manage_users, manage_groups, manage_acl, view_audit, manage_policies`）。示例角色：系统管理员、组织管理员、部门管理员、权限管理员、审计员、普通成员。角色名称只描述模板，不可直接当权限边界；必须有明确能力和有效范围。

- `system_admin` 全局豁免现有资源读取授权，但受审计、事务、版本、锁、禁用会话和危险操作规则约束。
- `org_admin` 可管理经授权的组织/账号范围，不因任命自动拿到任何文件的下载权限。
- `department_admin` 的组织管理范围限制在指定部门和子部门，不能因部门归属自动编辑其他部门文件或更改 ACL。
- `permission_admin` 仅可处理明确委托范围内的 ACL，不能越权自我授权、提权到全局、授予超过自身可委托的能力。
- `auditor` 可以读取脱敏审计，不自动获得文件内容的预览、下载权。

数据库模式（未来单独迁移）可采用 `management_roles`、`role_capabilities`、`role_bindings(subject_id,role_id,scope_kind,scope_id,expires_at)`，将系统能力和具体文件动作物理分离。需新增授权作用域证明、角色委任上限、禁止最后一位系统管理员被移除、自我提权阻断、角色变更即时失效、审计与撤销回归等规则。P0 **不创建这些表**。

## 6. 严格分层架构与代码落点

按现有 Go ports-and-adapters / React features 的约束实现，不绕过架构门禁。

| 层 | 推荐落点 | 责任 |
|---|---|---|
| React page/composition | `web/src/pages/Org.tsx` | 处理路由参数、模式组合、权限页入口 |
| React organization feature | `web/src/features/organization/OrganizationPanel.tsx` + 拆分出的 `PermissionsPanel.tsx` | Tab 切换、管理交互；`OrganizationPanel` 不继续无限膨胀 |
| 共享可视组件 | `web/src/shared/ui/` | 不含业务请求的目录选择器、表格、主体搜索控件 |
| 前端 API | `web/src/features/organization/api.ts` 或专门 `permissions/api.ts` | 类型化请求、错误映射、游标、刷新状态 |
| Go HTTP | `internal/httpx/` | 参数校验、受保护的路由、稳定输出契约 |
| Application | `internal/application/grants.go` + 可选 `permissions.go` | 管理鉴权、use-case、事务、审计、缓存失效 |
| Domain | `internal/domain/acl.go` | 纯权限决策规则及解释值对象 |
| Ports | `internal/ports/` | 批量/分页查询抽象，避免 Go 业务逻辑耦合 SQL |
| PostgreSQL adapter | `internal/adapter/postgres/` | 用索引/CTE 高效解析直接授权、祖先链、组归属与共享来源 |

**禁止**：`features/organization` 直接 import `features/folders` 的 API/私有组件绕过层级规则；前端私自解码 `is_admin`、应用路由层充当最终授权控制；为每个单元格做一次单独查询。推荐将共同的纯 UI 放到 `shared/ui`，共同数据 API 经明确的组合层组织。

## 7. 性能、一致性与审计

- P0 优先使用已存在的 `ix_acls_folder` / `ix_acls_subject`、`workgroup_members` PK 和目录父链结构；新增索引必须通过远端 `EXPLAIN (ANALYZE, BUFFERS)` 与实际数据集证实，不凭感觉叠索引。
- 用户/组选择器和 ACL 表分页/游标化；树节点懒加载/搜索，过滤去抖，后台查询中止或版本戳隔离，避免旧请求覆盖新选择。不能默认全量加载海量用户和所有目录授权。
- 读取自己的可用动作与列出别人的 ACL 明细分成不同权限边界；默认拒绝，主体不存在和不可见目录不泄漏详情。
- 在成功提交 ACL、组成员、账号状态、目录移动/继承变动和分享变动后统一令新请求重新鉴权。缓存失效不能早于成功提交；数据库提交失败不能污染缓存或假报成功。
- 权限查询和文件写入要复用服务端判定；保存文件和执行下载/预览时都必须重新校验，不因页面打开时有按钮而放行。
- 审计覆盖 grant.create / grant.revoke、role.assign/revoke（P2）、group.member_add/remove、账户冻结、涉及提权的拒绝事件；包含 actor、请求 ID、对象、来源摘要、前后差异及结果，不记口令、session、原始 cookie、文件正文。
- 可执行的性能目标由负载环境、数据规模、p95 API 延时和误判数的验收脚本正式定稿；任何页面流畅承诺都需要远端压测证据。

## 8. UI 视觉与可访问性

沿用 `docs/design/PRECISION-WORKBENCH-V2-SPEC.md` 硬朗、紧凑的蓝白工程设计：40px 顶栏、34px 操作条、标准 32px 行（可选 26px）、240px 左侧树、1px 分割线、低圆角。不要新增大量卡片式仪表盘、渐变大背景或占用高度的装饰。

- 1366×768、1440×900、1920×1080 三档布局基线；树和表格各自正确滚动，工具栏固定。
- Tab 使用 `role=tablist/tab/tabpanel` 且支持键盘；可见焦点和错误信息配合 `aria`；中文权限名称和技术 action key 明确对应。
- 操作前、请求中、部分失败、网络状态未知、无访问权、无直接 ACL、存在继承等状态必须彼此可区分。
- 一致使用既有品牌 Logo/Token，不另外造安全色彩体系；授权来源可用非颜色文本标签区分“直接/继承/分享”。

## 9. 交付分期和验收门禁

### G0：P0 设计冻结与安全基线

- 锁定交互方案与本合同；与主 SPEC §2、ADR-UX-04 对齐。
- 修正 `ListGrants` 读取他人 ACL 的权限边界，进行非管理员、禁用账号、猜测 folder ID 的负例测试。
- 核查 ACL 写入/撤销和工作组成员变更的缓存失效与事务一致性，覆盖并发测试。
- 不改变 `manage_acl` admin-only 的现状，不引入未审定的委派权限。

### G1：P0 组织界面整合

- `/org` 增加第三 Tab，支持 URL 深链和资源树，复用已存在的 ACL 服务端 API。
- 文档页的“管理权限”跳转统一入口；不产生两套授权写入流程。
- “按目录”直接授权表格、创建/撤销、过期和范围配置可完成完整闭环；普通员工看不到他人 ACL。
- 各种加载/失败/无数据/跨页焦点与不同尺寸的真实浏览器验收。

### G2：P1 有效权限解释、主体视图与审计

- 获得 ADR-UX-04 批准后上线服务端解释接口，与实际 `resolveActions` 共享规则、测试证明一致。
- 展示直接 / 工作组 / 继承 / 分享 / admin override 的具体来源，撤销后再次查询不会将仍存在的其他来源误判为没有权限。
- 加入主体搜索的权限范围查询和分页，管理员可按主体定位权限。
- 审计页面仅在已具备查询 API 和权限控制后启用。

### G3：P2 管理角色（单独里程碑）

- 新迁移 + 管理能力枚举 + role binding + scoped delegation + self-escalation safety + last-admin safety。
- 角色入口只有在全链路鉴权和审计完成并通过测试后开放；不能把新增角色标签当作 RBAC 已实现。

|---|---|---|
