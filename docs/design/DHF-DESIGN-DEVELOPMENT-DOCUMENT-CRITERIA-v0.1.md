## 1. 不可改变的已确认原则

1. Finder/文件管理继续作为真实文件与版本的权威来源；Notion 式知识页面独立建树，与文件夹通过显式关系双向关联，关联不赠送 ACL。
2. 文件夹知识首页默认手动关联；授权项目模板可以自动创建知识首页和文件夹结构，创建动作必须幂等。
3. 阶段验收默认严格；仅已发布授权模板允许申请有条件通过，实际放行必须有独立批准、有效期、受限动作、每项整改及关闭记录。
4. 阶段交付采用固定的资源 ID、修订序号和证据哈希；提交批次、审批历史与原始审核证据只追加，不得覆盖。
5. G6“设计开发转移阶段（第一次）”与 G8“设计开发转移阶段”是两个不同 Gate；任何名字近似都不授权合并。
6. 越级授权不得自动免除中间责任；职责分离、文件 ACL 与项目业务授权分别计算。
7. 本准则只规定**如何收集、核实、管理与批准规则**，不得反向声称 XMind 已明确指定全部交付义务、验收人或依赖图。

## 4. G6→G7→G8 的验证血缘和门禁

- **G6 L115–L129**：首次设计转移，包含工艺文件候选、送检样机、试产申请、样机检验、试产总结与转换评审候选；不是 G8 的重复。
- **G7 L130–L159**：验证记录候选，涉及工艺、包装运输、软件、特殊过程、非临床研究、稳定性等；其中“范例”“模板”“重复”须分开裁决。
- **G8 L160–L164**：转移/转换评审候选，含 L163“新建 DOC 文档”占位，不能作为正式交付要求。
- **G9 L165–L171**：设计开发确认方案、报告和阶段评审记录候选；L166/L168 同名需核实。

未来的受控关系应至少区分：`design_output_version`、`transfer_used_version`、`verification_subject`、`verification_result`、`stage_decision`。每一条引用以实际项目、文件 ID、版本、SHA 和审查决定为准；同名或同编号只产生待审候选关联。

**原文没有正式给出九阶段完整 DAG。** 后续 Gate 依赖必须在模板审核时明确授权，不得凭数字自动生成 G1→G9 的强制串行依赖。

## 6. 一条 DHF 开发文档的最小元数据

每份被纳入正式项目交付的记录/文件，至少应能够确定：

| 项目 | 最低约束 |
|---|---|
| 项目与阶段身份 | `project_id, stage_id, submission_id`（正式提交后） |
| 来源要求 | 永久 `requirement_id`、来源 UID、模板版本与要求修订 |
| 文件身份 | `file_id`；非文件证据则需具体资源类型/ID |
| 固定内容 | `version_seq, sha256` 或知识页面 `revision_id/content_hash` |
| 生命周期 | 草稿、待审、批准、失效、归档等状态来自对应权威服务 |
| 责任 | 编制/复核/批准/整改/独立验证的具体人员及授权快照 |
| 证明 | 创建、修改、批准时间；签署决定 ID；审计链 |
| 业务有效性 | 适用性、必需性、关键性、可否延期、接受标准 |
| 保留 | 与文件生命周期、证据 Hold、审计期限相容的策略 |

同一文件可以在多个阶段被引用，但必须每次重新判定对应阶段的要求是否满足；“共享文件版本”不意味着“共享阶段审核决定”。

## 7. 阶段交付与验收规范

1. 只有已发布且仍有效的模板版本才能产生正式阶段验收任务；草稿项目允许准备知识页面或文件，不代表可正式放行。
2. 必需证据不是只检查存在：必须判定关联对象真实、当前可验证、固定版本正确、要求的审批已完成。
3. 阶段提交必须冻结模板、要求集合、依赖集合、证据清单及审批责任链的身份和哈希，并进行事务性完整性校验。
4. 默认只有正式通过或退回；启用条件放行时必须有模板许可、具体授权、非阻断范围、逐项整改、截止期、验证人及明确允许动作。
5. 条件放行不能自动授权受控文件正式发行、不能自动传递到非直接下游阶段；逾期停止新的受影响受控转换而不改写历史决定。
6. 整改执行、独立验证、最终关闭三种决定分离；返修/退回形成新提交批次，不能覆盖原证据。
7. 已通过阶段的重大问题应创建变更评估/重新开启记录，不直接覆盖已批准历史。
8. 审批任务的存在和文件 ACL 是两个不同问题：任务授权不默示文件下载权限；应检查实际 ACL 或明确的最小证据访问授权。
