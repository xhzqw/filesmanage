# filesmanage 开发文档准则（Engineering Documentation Standard）

> 文档 ID：ENG-DOC-STD-001  
> 版本：v1.0-draft · 日期：2026-10-24  
> 责任：项目维护者 / 文档评审者（正式角色待指派）  
> 适用：本仓库 `docs/`、设计合同、API、DDL、测试证据，以及 DHF/CDW 相关开发交付  
> 状态：**开发分支待评审**。本文件合并前不是 `main` 的已生效规则；合并不等于 DHF 业务 SOP 获批。

## 0. 目标及边界

建立工程文档的唯一入口、命名、版本、变更、依据和验收方法，确保任何新功能能从“原始来源 → 用户决策 → 设计合同 → 代码/迁移 → 测试 → 部署证据”双向追踪。

本准则管**研发软件工程文档**。产品设计开发 DHF 文件的分类、交付和阶段验收另见 [DHF 文档与 Gate 准则](design/DHF-DESIGN-DEVELOPMENT-DOCUMENT-CRITERIA-v0.1.md)。两者不得混为一张表或互相替代审批。

## 1. 事实来源和效力

| 类型 | 权威用途 | 不可越界解释 |
|---|---|---|
| 当前 Git 提交的代码/DDL/测试、实际运行环境记录 | 证明具体版本已经实现、运行或测试的事实 | 静态代码不能证明部署、测试通过 |
| `AGENTS.md`、已批准的工程规范和 ADR | 开发及运行的硬约束 | 草案不得静默覆盖 |
| 用户明确确认的设计决议 | 约束后续设计方案 | 尚待讨论的建议不能冒充决议 |
| 原始 DHF XMind / 受控企业文件 | 证明来源原文、原始编号及历史内容 | 文件名不等于必交义务、真实审批或受控生效 |
| 设计草案、外部资料、AI 建议 | 供讨论、预检、验证 | 未签审时不可当成生产验收规则 |

发生冲突时，不得静默修改原文；登记差异 ID、冲突双方、适用范围、风险、建议处理、审批人、批准日期与替代版本。涉及法规或 SOP 的解释交由有权的业务/质量人员确认。

## 2. 工程文档必须具备的元数据

每份新增的规范性文档在开头写明：`document_id`、标题、版本、状态、发布日期或编写日期、作用范围、责任角色、来源链接/来源 SHA（如有）、相关 ADR、关联代码路径、评审和批准情况。保留旧版文件或 Git 历史，禁止无迹替换已批准版本的实质内容。

允许的文档状态：
`draft` → `in_review` → `approved` → `superseded`（也可 `withdrawn`）。

- `draft`：建议，不代表已经支持。
- `in_review`：已提出审查，不代表获准实施。
- `approved`：授权主体已审定其适用范围；必须可追踪决定。
- `superseded`/`withdrawn`：保留历史与替代指针，不能删除已被审计引用的旧版。

**Git 合并、PR 关闭和业务批准是三种不同事件**；不得以提交成功取代正式质量验收。

## 3. 文档类型及存放位置

| 类型 | 存放 | 最低要求 |
|---|---|---|
| 产品/系统规格 | `docs/SPEC-*.md` | 范围、需求 ID、行为、权限、验收、版本 |
| ADR / 设计合同 | `docs/design/` | 决策状态、备选、权衡、约束、变更影响 |
| DHF 开发文档准则与来源映射 | `docs/design/DHF-*` | 原文 ID、要求候选、证据/审批边界 |
| API 合同 | `docs/openapi-implemented.yaml` + 设计文档 | 请求/响应、错误、授权、幂等、兼容 |
| DDL / 数据迁移设计 | `docs/design/`；执行版在 `migrations/` | 不变量、事务、并发、回滚、测试 |
| 测试和证据 | `docs/TEST-EVIDENCE.md`、`docs/evidence/` | 运行环境、命令、代码 SHA、结果与异常 |
| 操作/部署 | `docs/OPERATOR-RUNBOOK.md` 等 | 适用环境、审批、备份、复原、故障排查 |

命名建议：`<DOMAIN>-<SUBJECT>-v<major.minor>.md`；必要时日期后缀。正式记录应在文内用不变的文档 ID，不能依赖文件路径充当业务身份。

## 4. 规范性措辞

- **必须 / SHALL**：获批范围内的阻断性合同；应有一条或多条可验证验收项。
- **应 / SHOULD**：建议默认实现；偏离须说明原因。
- **可 / MAY**：明确的可选能力。
- **待核准**：不得作为正式 Gate 条件。
- **代码已实现**：仅当指明 commit、路径和实际行为。
- **测试已通过**：仅当有真实测试结果、环境、运行时间和提交 SHA。
- **已部署**：仅当实际环境完成启动、健康检查及复验。

文档里的示例项目、人名、文件编码不自动成为实际配置或企业受控编号。

## 5. 一个功能的最小文档交付

任何跨后端、数据库、前端或工作流的业务功能，在进入实现前/随 PR 同步补齐：

1. **需求**：稳定 ID、原始来源及已确认决策；未决事项和阻断优先级。
2. **行为**：状态机及合法迁移，角色能力和职责分离。
3. **数据**：实体、主外键、唯一/检查约束、保留策略及数据库锁顺序。
4. **接口**：方法、端点、输入输出、错误码、幂等键、CAS/并发及权限检查。
5. **前端**：入口、成功/失败/重试、危险操作确认、权限失效、加载和响应式契约。
6. **验收**：单元、集成、权限负例、并发、真实浏览器和回归，需列用例 ID。
7. **交付证据**：Git 提交、迁移版本、远端测试命令与实际结论、部署环境及回滚说明。

新增 API 应与实际 `docs/openapi-implemented.yaml` 和生成脚本保持一致；生成器尚不能表达的行为记录明确的偏差和阻断项，不得编造端点。

## 6. 可追踪性与变更治理

工程需求、决定、变更与测试分别拥有独立稳定 ID。至少维护以下链路：

`source_id -> requirement_id -> decision_id -> design_contract_id -> code_path/commit -> test_case_id -> execution_evidence_id`。

- 稳定 ID 与源文本行号分离。行号仅作定位别名。
- 不以文件名、XMind 标题数量、重复文本或表单编码作为实体主键。
- 涉及不同项目、模板版本、阶段或提交批次的数据必须有身份/复合约束，避免串版。
- 变更已经发布的合同必须新建版本或受控修订；记录差异、影响、批准和旧版保留。
- 任何缺失前置材料的场景都应 `NO-GO`，而非省略检查后放行。

## 7. 审查合并及发布门禁

| Gate | 审查问题 | 不通过条件 |
|---|---|---|
| DOC-01 | 来源、权威级别和批准状态是否完整？ | 草案被写成正式制度 |
| DOC-02 | 每条“必须”可追踪到要求/批准及测试？ | 缺少来源或验收依据 |
| DOC-03 | 状态机、权限、失败路径、事务完整？ | 仅有 UI 操作说明 |
| DOC-04 | API、DDL、Go/TS 类型与现行代码一致？ | 把尚未实现的功能称为已交付 |
| DOC-05 | 安全、数据保留、保密边界可验证？ | 失权、覆盖历史、证据丢失风险 |
| DOC-06 | 测试和发布声明有真实证据？ | 没有执行却标记 PASS |
| DOC-07 | 是否完成差异、ADR 和回归记录？ | 静默改变既有决议 |

所有构建/测试/浏览器与数据库验证须遵从仓库 `AGENTS.md` 所述远端运行规则。不得泄露 `.secrets/` 中的口令、令牌或内部证据。来自业务的原始文档和个人信息未经适当授权，不得整份提交到公开仓库。

## 8. 本次 DHF 特例

- G1–G9 的**真实名称和原文行号**采用源文件；来源 SHA 见 DHF 专门准则。
- G5 软件、生产工艺和 G6 首次转移为受控试点；“候选交付”并非必交文件。
- G6（首次转移）与 G8（设计开发转移）拥有独立阶段身份。
- 文件版本、审批、阶段 Gate、条件放行、整改和签收均需独立业务记录。
- 默认严格验收；有条件通过只能来源于已发布授权模板及本次独立决定。
- 在业务签审、数据库安全与远端测试前，DHF 试点不得被宣称为已上线。
